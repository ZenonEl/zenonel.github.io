Colophon

Colophon

Static HTML generated from a content model by a Python script with no dependencies. Nothing on a page reaches outside the site, and no page runs any script.

Last reviewed 2026-09-07

01How it is built

Every entry is a JSON file with an en and a ru block. A generator in the Python standard library reads them, checks them against the case and project schemas, and writes the whole site.

Stories have their own headings. The build checks that both languages contain the same sections in the same order, that the text is not empty, and that older fragment links still have a destination. Other entries still use the original fixed section schema.

One rule is newer than the rest and worth naming. A required section that carries nothing but an owner-input marker also fails. Structural presence was too easy to satisfy, and an empty section under a real heading reads as an answer.

02Evidence marks, and two kinds of blank

The content model records sources and publication limits for editing. Pages show only the marks that help a reader: measured, public repository and published specification. Employment provenance and deliberate redactions remain in the model; they are not displayed as badges.

A blank space on this site is one of two things, and they are marked differently because they mean different things.

Detail withheld
A decision. The fact exists, it would identify a client or a system, and it is not going to be published. The reason travels with the mark.
TODO: owner input
A gap. Something is missing that could be published, and until it is quoted from a source it stays visibly missing.

03What it does not use

  • No framework and no build toolchain. The generator has no dependencies outside the standard library.
  • No script of any kind. Stepping through a diagram is links and :target, so the page that arrives is the page that works.
  • No analytics, no embeds, and no request to any other host.
  • One web font, served from this site, under an open licence, in two subsets.
  • One icon set, thirteen files, vendored and inlined. No icon font.
  • One diagram engine, run at build time and never in a browser. The committed SVG is what ships.

04Type, surface, and ink

The site follows the reader's system colour scheme: graphite at night and soft paper by day. If the browser reports no preference, graphite is the default. Geometry, type and hierarchy do not move between them, so these are two palettes for one design rather than two different pages.

Both palettes use three surfaces: the page, an inset panel, and a sheet on the panel. Text is near white on graphite and deep green-black on paper. Structure is carried by one-pixel hairlines in two weights: a quieter one inside a list and a firmer one where a section starts.

Headings are set in Lora, a screen oriented serif with calligraphic roots, published under the SIL Open Font License. It is served from this site in a Latin and a Cyrillic subset, so Russian headings come from the same drawing as English ones instead of falling through to whatever serif the machine happens to have. That was the reason for adopting it: Cyrillic display type through a fallback stack reads sharper and less controlled than the Latin beside it. Body text uses the platform sans and metadata uses the platform mono.

Softness comes from spacing and curvature, not from blur. There is no shadow anywhere in the stylesheet, and no decorative mark. Every line on a page separates, connects, or classifies something.

One botanical green accent, tuned separately for graphite and paper, appears only where it carries meaning: the current page, a hovered link, a gate on a diagram, a section number, an evidence mark. Every text colour is checked against WCAG 2.2 AA on all three surfaces in both palettes, and the lines that carry information clear the 3 to 1 ratio for non-text contrast.

Print uses a third palette, plain black on white. Navigation disappears and external link addresses are written out, so a printed CV or case remains readable without its screen chrome.

05The shape of a record

A deep record is a sheet with a margin. The margin holds what the record claims: its status, the date it was last reviewed, its evidence marks, the sources behind it, and the links it points at. The column beside it holds prose and nothing else.

The margin also holds the contents of the sheet, numbered in reading order, so a reader can jump to the verification section without scrolling past the architecture. Below the breakpoint the margin becomes the first block, which is the order a phone needs anyway.

06Icons, and what they are not allowed to do

Thirteen concepts carry an icon: public repository, specification, measured evidence, self-reported, detail withheld, tests, checks, release, external link, related material, language, architecture, and people. They come from the MIT licensed Iconoir set, and only the thirteen files this site uses are vendored into the repository.

There is no icon font and no request. Each icon is inlined into the page at build time from one helper, so a concept is drawn the same way everywhere and adding one means vendoring a file rather than pasting markup.

An icon supports a label and never replaces one. A decorative instance is hidden from assistive technology in the markup, the word beside it stays, and the validator fails a link whose only content is an icon.

The licence ships with them at /assets/icons/LICENSE.txt.

07Checks

tools/build.py refuses to build content that breaks the schema. tools/validate.py checks the generated site: internal links and fragments, page metadata, language parity, the rendered section schema, dash usage and a short list of canned phrases, the absence of script and of any external request, the self hosted font declarations, and the publish boundary.

The privacy check is stored as digests of stems rather than as words, because a linter that spells out the identifiers it protects has already published them. Hashing stems rather than whole words is what catches an inflected form. A single word can be tested against the list with tools/validate.py --check-token.

HTML validation runs separately with html-validate, and the commands are in the README.
