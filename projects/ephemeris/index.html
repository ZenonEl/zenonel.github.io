ephemeris

First there were just dailies

Ephemeris grew out of a habit. In May 2026 management wanted to know what had been done each day without a call and without asking everyone by hand every evening. On 6 May I set up a separate repository for dailies: one issue per pair of date and project. There were no standards at all then, only the idea.

A GitHub repository with issues as dailies turned out to be close to ideal. They are linked to the team's projects, commits, tasks and other dailies can point to them, and GitHub takes care of storage, edit history and versions. On 11 May a README with rules appeared, on 14 May a body template, and in July rules for labels, for links between repositories, and for writing the body for people while the details go into comments.

Over time management seems to have stopped reading the dailies, and I kept writing them. As far as I know nobody else on the team treats them this way, yet the dailies and git gave me an almost complete history of my projects: I can go back to any day, and together with the mnemo archive the source material behind the decisions is visible too. On 30 September 2026 the work repository held 236 of them.

From habit to protocol

By late July the dailies had a settled standard, section order and recurring wording, and it became clear they could be kept by rules rather than from scratch each time. My work day is longer than one agent session: the context gets compacted, the session ends, and the next one has to continue from the same place without rereading the whole conversation. Without rules every session kept the daily its own way.

The ephemeris concept appeared on 31 July 2026 and the first commands on 6 August. There are five now: open a daily, update it during the day, hand over a session, hand in the day, and resume from a handoff.

A handoff is an address map, not a retelling

The main rule of ephemeris is that a handoff says where things are: a comment number, an issue or PR, a commit, a file path, a link to a record in mnemo. The next session goes through each address, opens what it needs and names aloud whatever did not open.

A retelling would be a second copy of what is already written nearby, and over time it would drift from the original. An address costs almost nothing, and the choice of what to read stays with whoever continues the work, not with whoever wrote the handoff yesterday.

Work and personal apart, several sessions in one day

Work and personal dailies live in different repositories, not under different labels in one. The repository addresses sit in a configuration outside the package. If the project does not make the contour clear, the agent has to ask rather than choose.

On 31 August markup for several sessions in one daily arrived. Each session keeps its own block between markers and leaves the others alone, and in the shared lines the owner of a task is named by the session's name rather than “mine”. The day is handed in by whichever session does it first, and the others add their own handoff below. A “ready to close” label and a weekly cleanup close old dailies only after confirmation.

Instructions, not an application

There is no service and no background process inside: only the skill, the commands and one script that checks the version across three manifests and two README badges. Both hosts compare only the version number, and a stale manifest means an update never reaches installed copies while the update command reports everything as current.

Ephemeris reads the daily template from the README of the dailies repository every time and keeps no copy of it: reporting formats change, and a copy inside the plugin would fall behind in silence. Since 26 August the package installs from the Claude Code and Codex marketplaces.

Where it stands

The latest version, 0.8.1, came out on 22 September. Ephemeris keeps my work days and the days of this site; in my work dailies from 18 to 28 September its markup appears in 15 of 21.

Together with mnemo and herald it covers one path: a message arrives through herald, the material goes into mnemo, and ephemeris keeps the course of the day and the addresses for the next session.

From the start I planned the links between the tools in this set to be soft. Ephemeris writes addresses in the mnemo format and uses skills such as humanizer when they are installed, but depends on none of them: without mnemo there is simply no archive link, without humanizer the text stays as it is.

How it is built

Architecture
  • One skill and five commands, one per operation of the day.
  • Archive addresses are written as mnemo citations and checked on resume.
  • The daily template is read from the dailies repository; the package holds no copy.
Infrastructure
  • A plugin and a skill from one directory for Claude Code and Codex, installed from the marketplaces.
  • The GitHub CLI for issues; repository addresses in a configuration outside the package.
Fault tolerance
  • Resume walks every address and names the ones that did not open.
  • An ambiguous contour means asking a person, not choosing a default.
  • The version check script catches a stale manifest.
Data and AI
  • Work and personal dailies live in different repositories.
  • A handoff never records what the session did not do.
Decisions and assumptions
  • Dailies as issues in a separate repository: links to the team's projects, history and versions with no infrastructure of my own.
  • An address map instead of a retelling.
  • A session and a day are different units: handing over a session is not handing in the day.
  • The first to hand in the day does it; the others add their own.
  • Soft links to mnemo, herald and skills such as humanizer: it works without them.
