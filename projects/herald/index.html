01Origin need

Agent sessions need to receive project material and, less often, to send something back. Doing that through whatever channel is at hand puts an agent one mistake away from writing to the wrong person.

I wanted the communication edge to be a small component with an explicit boundary rather than a capability scattered across prompts.

02Who it is for

Me, on projects where an agent needs the day's incoming material. More generally, anyone who wants agent output to pass a human before it reaches a client.

03My role

Author. The gateway, the route model, and the test suite are mine.

04Architecture

Herald runs locally and speaks MCP. Incoming messages and files land in a temporary buffer that mnemo imports from, so herald never becomes a second archive.

In the other direction it sends material an agent has prepared, but only to destinations and file roots that exist in configuration outside the repository.

05Design decisions

  1. The allow-list lives outside the repository

    Destinations and file roots are configuration, not code. Nothing in the public repository names a real channel, and cloning the project does not hand anyone a route.

  2. The buffer is deliberately temporary

    Herald captures and hands off. Storage, provenance, and long-term structure belong to mnemo. Two components with narrow jobs are easier to reason about than one that does both.

  3. Herald does not decide when to write to a client

    It moves prepared material through an allowed route. Judging whether a message should be sent at all stays with the person.

06A correction I had to make

A concrete correction is public in commit b0bff52. An agent preparing one client update could append unrelated project problems and downstream questions because the tool described relevance but did not make the requested subject a hard boundary.

The correction made every field stay inside the requested subject and limited questions to the first unresolved dependency that blocks the next action. Tests now assert those two phrases in the tool contract. This checks the instruction surface, not every response an agent can produce.

07Tests, CI, releases

At reviewed beta/watch commit f55c0ab, pytest collected and passed 140 tests. The same workflow runs tests and builds the package in CI; server-side CI status was not checked here.

The count belongs to the beta snapshot and will change. It does not establish coverage or live-channel reliability.

08Privacy boundary

Herald handles material that belongs to other people, so the design keeps the sensitive parts out of the code: routes, file roots, and credentials are configuration supplied by the operator.

The allow-list stops an accidental route from being invented at send time. It does not defend a machine that is already under someone else's control.

09Limitations

  • It runs locally and is built around one operator, not a team deployment.
  • An allow-list constrains where material can go. It cannot judge whether the content should be sent.
  • The value depends on mnemo being on the other side of the import.

10Next steps

Herald is deliberately narrow. A useful next change would remove friction from the handoff to mnemo or make a refused destination easier to understand. Adding another channel by itself would not improve the boundary.

11Reproduction path

The test directory is the fastest honest read: it shows which behaviours are pinned and which are not.

The README carries separate marketplace installation commands for Claude Code and Codex, then requires operator-owned routes and credentials outside the repository.
