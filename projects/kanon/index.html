kanon

A Claude Code plugin and Codex skill. Before work starts, it turns a task into a checklist of observable results and the proof each one needs. An item closes when proof is inserted; a tick is not enough.

Where it came from

kanon appeared after yet another complaint from a colleague: he gathered material with Claude, discussed everything, and then Claude did it its own way. It happens to me too, but noticeably less often, so I went to find out where the difference was.

Shortly before that I had read about the harness: an agent is a model plus everything around it, instructions, context, tools, memory and checks. When an agent does the wrong thing, “is the model stupid?” is almost always premature: first ask whether it knew the rule, whether it could learn that it had done badly, and whether it could see what it needed. I went through the idea with Claude together with my own tools, mnemo and the rest, and saw a gap they do not close. Agents usually get plenty of instructions and almost no checks that go red, and the usual cure is yet another paragraph of instructions.

Gathering eats the context window

Before the work, an agent gathers material, and that eats the context window. The work itself runs on what is left. The agent does not ignore what it gathered; it can no longer see it. Hence the familiar symptoms: “I did it from memory”, one screen checked out of ten, one version where several were asked for, and “what next?” after every step.

Post-mortems of such failures usually blame character: rushed, read it carelessly. That cannot be fixed. The cause is the same in every case: between “understood the task” and “started working” there was no step that turns the task into a list where a shortfall is visible.

A checklist before the work

kanon adds that step. Three questions, and each has to produce lines in a file. What must exist for the task to count as done: results, not actions, and a number in the task becomes a number of lines. What proves each item: a command, a screenshot path, a commit hash. What from the gathered material has to reach the result.

Then one rule that holds the rest together: an item is closed by inserting proof, not by a tick. “Done”, “checked” and “works” without proof read as an open item. The file survives what the context does not: compaction, a new session, a different agent.

This is not a to-do list

A to-do list answers “what to do”. A kanon checklist answers a different question: “how will I know it is done”. Each item names its check, closes with proof, and the number of lines is compared with what the task asked for. It is written before the work, while the gathered context is still fresh.

Compared with familiar documents, a PRD says what we build, a plan says how we build it, and kanon says how we accept it: what counts as proof and on what grounds an item can be closed.

Any session comes back to that file: after context compaction, a new one, or someone else's entirely. Even when the agent's context has swollen and something has dropped out, the agent does not try to remember; it looks at the file and checks against it. And checklists do not pile up: each has a lifetime, open, closed or stale, and a separate script proposes what to do with it next.

A program checks the rules

A rule nobody watches holds for about a week, so code checks the rules that can be checked. The linter refuses a tick without proof, proof from a list of empty claims, and a line count that does not match the task. A separate script works out a checklist's lifetime, open, closed or stale, and proposes an outcome, but deletes nothing by itself.

Hooks speak at the start of a session, once before the first write without a checklist, including through the shell, and at stop if items are still open. Nothing blocks: a hook that gets in the way gets uninstalled with the plugin, so a hook that crashes exits with zero in silence. A checklist can be written in any language; the machine words have aliases, currently in Russian and English.

Three days and six review rounds

I built it in three days, 2 to 4 September 2026: 20 commits up to version 0.12.1. On 2 September alone there were six review rounds, three of my own and three independent ones from a second model; one of them found a P0: a hard link bypassed a fix that was already in. On 3 September the hooks started working under Codex, and a live session confirmed the stop hook. On 4 September two rules from someone else's analysis of similar failures were added.

The checks rest on a test bench: 43 mutations break the linter and verify that the tests notice, the self-test makes 61 checks, and a separate suite checks file parsing. CI is green on the latest commit.

What it deliberately does not do

kanon does not judge taste and does not check how well a task is split into items: a badly split task gives a green checklist over a bad split. It does not replace review: a closed checklist means “nothing was forgotten”, not “this is good”. The boundary is deliberate: a tool that promises more than it verifies is worse than none, because a green list starts being read as a guarantee.

The repository is private for now, and I will open it later. I keep kanon checklists on my work projects and in the work on this site.

The link to mnemo is soft, like everything in this set: a checklist item may carry a requirement number from the archive, and then a closed item gives ready proof for that requirement. But kanon works without mnemo, and mnemo without kanon.

How it is built

Architecture
  • A skill, commands, a linter, a lifetime script and hooks; the file format has its own specification.
  • An optional link to mnemo: an item may carry a requirement number, and closing it yields ready proof for that requirement.
Infrastructure
  • Python, Claude Code hooks, working under Codex.
  • CI on GitHub Actions: version checks, the mutation bench and the self-test.
Fault tolerance
  • A hook never blocks and exits with zero in silence on an internal error.
  • The reminder before the first write speaks once per session.
  • The lifetime script only proposes; a person deletes.
Data and AI
  • A checklist is a file in the project and survives context compaction and a change of session.
  • The checklist can be in any language; the machine words have Russian and English aliases.
Decisions and assumptions
  • Proof instead of a tick.
  • Remind rather than block.
  • Promise no more than is checked: taste and the quality of the split stay outside.
