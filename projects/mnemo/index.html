P-01Project

mnemo

I made mnemo because project requirements kept arriving in messages, files, and later corrections. It gives Claude Code and Codex a local archive with links back to the source, plus records of requirements, open questions, and the work done against them.

A forwarded message is part of the project too

In my commercial work, management handles the client relationship. I do the implementation, often working from a forwarded message, a document, or a video showing what someone has configured. Before changing the code, I need to understand what was requested and how it relates to the earlier discussion.

I wanted to keep that material in a form I could return to: who said what, when it arrived, what it referred to, and which later decision relied on it. Saving the chat history helps, but it does not tell the next agent session which requirement changed or where to look for the original explanation.

That became mnemo. I wrote the archive format, the Python tools, and a plugin for working with the archive from Claude Code and Codex. I use it on my own projects. It keeps the source material alongside the records I need to continue the work.

What happens to a new piece of feedback

An import keeps the material with its source information and gives it an address inside the project archive. A requirement or decision can then refer to that entry. The original stays available when the shorter working record is no longer enough to explain a detail.

For example, imagine a forwarded screenshot asking to change how a delivery option appears. This is an illustration, not a quotation from a client project. The screenshot belongs in the archive as a source. The interpretation of the request belongs in a separate requirement linked to it. If a later message changes the condition, that message should have its own entry; it should not erase the earlier wording.

The format separates fidelity from attribution. A screenshot may preserve visible text exactly while leaving it unclear who originally wrote it. A machine transcript may help find the relevant part of a recording without being suitable for a verbatim quotation. One confidence score would blur those differences.

Mnemo cannot recover an author or source that was never supplied. It can retain that uncertainty with the material so that a later summary does not silently turn it into a fact.

Keeping the files does not settle the task

Preserving material is one job. Figuring out what remains to be done is another. Mnemo has a work-state skill for requirements, open questions, and checks of completion claims against the archived evidence.

In the delivery-option example, importing the screenshot does not make the requested change complete. The requirement still needs an implementation and a check tied to that request. A question also needs to explain what is unclear and what has already been tried, instead of sending every uncertainty back to the person.

I keep those records linked to the archive because the next session needs both sides: the current work and the source behind it. The plugin helps maintain the records and check them. Deciding what a request means, whether an answer is sufficient, and whether the result is acceptable still involves me.

Herald brings material in; ephemeris carries the day forward

I use herald for the communication side. It captures incoming material in a local buffer, where an agent can pick it up for import into mnemo. It also lets an agent prepare and send an update through a configured channel. The capture buffer is temporary; mnemo holds the project history.

Ephemeris handles the daily record. In my workflow that means the daily issue, its body and development-log comments, with links back to the relevant mnemo entries. That gives the next session somewhere to start without having to reconstruct the entire day from chat.

The projects can be read separately, but this is why I built them to work together. A new message has a route into the archive, work has a place to be recorded, and the next session has references to follow. The workflow page shows that route across the tools.

A live project corrected the archive itself

On 8 September 2026, I used mnemo to assemble every open question on an e-commerce project, with a source address beside each one, and put the complete list in front of management. The reply exposed one conclusion drawn too quickly, so I returned to the primary source and corrected it.

Six days later, work on the same project exposed two defects in mnemo's reconciliation logic. Both were fixed in the tool that day and released as 0.15.1-beta. The project supplied material to the archive and showed where the archive's own rules were wrong.

The archive's own write path needed work

Importing material safely took several corrections in the public history. An early rollback fix still had a bad window: an interruption after the manifest had been saved could make the importer treat a completed import as unfinished and remove its files.

The next fix based that decision on the manifest state on disk rather than on signal-handler timing. A further correction limited the saved-state check to material belonging to the current operation. That detail matters when an import is deciding what it is allowed to undo.

The published standard describes the archive rules. A self-check compares the standard and the implementation, while the test suite exercises their behaviour. At the reviewed commit 5e0417c, the CI commands were also run locally on 7 September 2026: the self-check and all 64 unittest tests passed.

To try mnemo, start with the repository README. It gives installation instructions for both hosts; the Python tools use the standard library. The format specification is available separately if you want to inspect how the records work before installing the plugin. The archive is local working material, so using mnemo does not make private project files suitable for publication.
