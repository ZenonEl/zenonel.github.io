01Origin need

Sharing media between people through a chat client runs into two limits at once: what the hosted API will accept, and what happens to a long download when the process restarts.

The project exists to solve both on hardware the operator controls.

02Who it is for

People who self-host their own tools and are willing to run a container to avoid a third party in the middle.

03My role

Author. Architecture, implementation, tests, and the documentation site are mine.

04Architecture

A request is written to the database before any download starts. Workers claim from the queue and run a chain of downloader backends, and delivery can go through an optional local Bot API server.

  • C# 14 on .NET 10, packaged for Docker as the intended way to run it.
  • SQLite reached through Dapper, with FluentMigrator owning the schema.
  • Modular yt-dlp and gallery-dl backends behind one downloader interface.
  • Concurrency is bounded by a semaphore sized from configuration, three at a time by default and capped at twenty.
  • Typed configuration that validates itself at startup rather than loose environment lookups.

05Design decisions

  1. Persist the queue instead of holding it in memory

    Media downloads are long and failure prone. Writing the work down first is what makes a restart a pause rather than a loss, and it costs a schema and a migration path.

  2. Downloaders behind one interface

    Sites break, tools get replaced, and one backend is never enough. A chain with a common interface lets a new backend enter without touching the queue or the delivery path.

  3. Local Bot API as an optional path

    It raises the file limit to 2 GB, and it also adds a component the operator has to run. Making it optional keeps the simple deployment simple.

06A correction I had to make

Until the middle of 2026 the queue existed only in memory. A crash or a reboot dropped whatever had been requested, and the person who asked got neither the file nor an explanation. The design read as durable on a diagram and was not durable in operation.

The fix was to write each request into a DownloadJobs row before the download begins, delete the row on completion, and re-enqueue whatever is left at startup through a resume service that also tells the requester what is happening.

It was checked by hand as well as in tests: a job was inserted, the bot was restarted, the download resumed and the media arrived, and the row was gone afterwards. What the change buys is at least once delivery, which is written into the code as a deliberate choice rather than left as an assumption.

Commite5ad06517 July 2026. Persists each request before the download starts and re-enqueues leftovers at startup.

07Tests, CI, releases

34 unit tests run on every push and pull request. They use xUnit with NSubstitute for the seams, and the CI job restores, builds in Release, runs the suite, and then starts the bot for two minutes so a configuration error cannot pass as a green build.

The latest published GitHub release at review time is v0.3.0-beta from 27 July 2025. The reviewed main commit is newer, so the release tag is not used as the current code version.

08Privacy boundary

The point of self-hosting is that the media and the queue stay on the operator's machine. Credentials and destinations are configuration, not code.

Self-hosting keeps the queue and media on the operator's machine. The project has not had an external security review.

09Limitations

  • Downloader backends depend on third party sites that change without warning.
  • The 2 GB path requires running a local Bot API server, which is a real operational cost.
  • 34 unit tests pin the core behaviour. They are not an end to end guarantee across every backend.
  • Delivery is at least once, not exactly once. The job row is removed only after a normal finish, so a crash between a successful send and that removal replays the whole job on restart and the recipient can get a duplicate. The code says this is the accepted trade: a repeat is preferable to a lost download.
  • Nothing here has been reviewed by anyone else. Self-hosted describes where it runs, not how safe it is.

10Next steps

The changelog is generated from commit history. It describes what landed and when; proposed work stays out of the release record.

I would watch two pressure points first: downloader backends move whenever the sites they read move, and the 2 GB path costs the operator a second component to keep running.

11Reproduction path

The repository ships a Dockerfile and a compose file, and the documentation site covers configuration in more detail.

After the required configuration files are prepared, docker compose up -d --build builds and starts the bot together with the local Bot API service described by that compose file.
