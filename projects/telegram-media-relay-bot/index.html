TelegramMediaRelayBot

A self-hosted .NET Telegram bot: it downloads media from a link through yt-dlp and gallery-dl and forwards it to contacts by their privacy rules. Started by hand in December 2024 and reworked in 2026; the download queue survives a restart.

Started by hand

I made the first commit on 4 December 2024. The idea is simple: a person sends the bot a link, the bot downloads the media and forwards it to contacts, and each contact has its own rules about what it wants to receive. Most of the first version was written by hand: the database, contact invitations, privacy, muting a contact.

v0.1.0-beta came out on 26 December and v0.2.0-beta on 20 January 2025. In 2025 I was working with the Gemini web chat, and v0.3.0-beta came out by 27 July. The busiest months were December and January: 49 and 85 commits.

The 2026 rework

From 27 to 30 March 2026 I reworked the project with Claude, through a branch and a pull request for each change. MySQL, a separate Tor library and dead code went away; errors started coming back as a result type rather than exceptions; Docker and a self-hosted Bot API server arrived, along with a test project, downloads in group chats, user states in the database and a download queue with a configurable concurrency limit.

On 17 July 2026 the project moved to .NET 10 and C# 14, and the same day the queue moved from memory to disk. The repository holds 376 commits in all.

A queue that survives a restart

Until July 2026 the queue lived only in memory. A crash or a reboot dropped whatever had been requested, and the person who asked got neither the file nor an explanation. The design read as durable on a diagram and was not durable in operation.

Now each request is written into a DownloadJobs row before the download begins, the row is deleted on completion, and at startup a resume service re-enqueues whatever is left and tells the requester what is happening.

I checked it by hand as well as with tests: I inserted a job, restarted the bot, the download resumed, the media arrived and the row was gone afterwards. Delivery came out at least once: a crash between sending and deleting the row repeats the job, and the recipient may see a duplicate. The code records this as an accepted trade: a repeat is better than a lost download.

Commite5ad06517 July 2026. Persists each request before the download starts and re-enqueues leftovers at startup.

How it works

The downloaders stand in a chain behind one interface: yt-dlp for video, gallery-dl for galleries, and the next one is tried if the previous one fails. Sites break and tools change, and a new downloader is added without touching the queue or delivery.

Concurrency is capped by a semaphore from the configuration: three downloads at once by default, twenty at most. Files up to 2 GB go through an optional local Bot API server: it lifts the hosted API's limit but is one more component the operator has to keep running, so it is off by default. Proxies can be set per site: HTTP, SOCKS5 or Tor.

Where it stands

On 30 September 2026 the project has 34 unit tests on xUnit with NSubstitute. On every push CI builds the project, runs the tests and then runs the bot for about two minutes so that a configuration error cannot pass as a green build; the last run is green. The latest release, v0.3.0-beta from 27 July 2025, is older than main, so the tag is not passed off as the current version.

The documentation site was built in July 2025 and still describes the previous version; the update sits in a separate branch. The downloaders depend on third-party sites that change without warning, and the project has had no external security audit.

How it is built

Architecture
  • A request is written to the database before the download starts; workers take jobs from the queue.
  • A chain of downloaders behind one interface: yt-dlp, gallery-dl.
  • Errors come back as a result type; the configuration is typed and validates itself at startup.
Infrastructure
  • C# 14 on .NET 10, Docker and compose as the main way to run it.
  • SQLite through Dapper, with FluentMigrator owning the schema.
  • An optional local Telegram Bot API server for files up to 2 GB.
Fault tolerance
  • A queue on disk and a resume service at startup.
  • At-least-once delivery, recorded in the code.
  • A semaphore caps concurrency at three downloads by default.
  • CI runs the bot for two minutes after the tests.
Data and AI
  • Media and the queue stay on the operator's machine.
  • Access, proxies and addresses are configuration, not code.
  • Each contact has its own per-link privacy rules.
Decisions and assumptions
  • Keep the queue on disk, not in memory.
  • Downloaders behind one interface.
  • A local Bot API as an optional path, so a simple deployment stays simple.
