W-01Case

Real orders before the official launch

I led the build of a PrestaShop store on a stack that was new to me: AI agents wrote the code, and every change went through subagent review until LGTM before production. Work began on 24 July 2026 and the first real payment went through on 9 September. From 9 to 29 September, before the official launch and with the site hidden from search engines, the store took 101 orders, 70 of them paid, and 347,980 RUB passed through its online till.

From requirements to real orders

This was my first project at this scale, and I led it from choosing the stack to real payments; AI agents wrote the code. Management talked to the client. The starting brief sketched a shop modelled on someone else's site, with no product marking, no warehouse, no Yandex Delivery and no partial prepayment. After that the scope was settled in management's chat with the client, and requirements reached me as messages forwarded from that chat into the project's work topic. I turned them into requirements, chose the technical direction and carried changes through review and acceptance. I owned the user flows, the boundaries between systems, production checks and the final engineering decisions.

The longest stretches went where good documentation does not exist: the Chestny Znak product-marking scheme with its legal side, the online till and MoySklad, several sole-proprietor sellers in one store, and the CDEK and Yandex Delivery APIs. Answers came from vendor docs, the text of government decrees, integrators' write-ups and articles on Habr, and were then checked against sandboxes and the production till. A live project turned out to be different work from the theory: a mistake here cost a real buyer money, a receipt or a parcel. For example, the seller of each order line is recorded at the moment of the order: otherwise moving a product to another sole proprietor would rewrite the past report by seller.

The shop had to support several sellers, take catalogue data from marketplaces, handle partial prepayments, synchronise stock and route orders to two delivery services. I chose PrestaShop after checking those requirements on a live stand. Its native model could represent the size ranges, the official YooKassa module installed without a patch, the delivery sandbox returned 13 rates and 20 pickup points, and an API stock write recalculated the aggregate. YooKassa was useful for validating the platform choice; for the production payment path management and the client later chose CloudPayments, and I built a custom module for it.

The store grew to cover catalogue imports, CloudPayments, online receipts, stock sync with MoySklad, marketplace data, CDEK, Yandex Delivery and product marking. On 29 September the repository held 22 custom modules. Checks run on hand-written runners: 13 suites and 1,343 checks on 22 September, and a separate run of 1,155 checks for marking on 23 September. The repository has no CI.

The first real payment went through on 9 September. The next day, an order completed payment, receipt, stock and delivery processing without anyone moving it by hand.

The catalogue passed the wrong check

One import increased the catalogue from 1,263 to 1,857 variants while reporting no errors and no duplicate size values. The source supplied point sizes such as 90; the store had already normalised the same size to a range such as 80-90. A string comparison treated them as different, so both survived on 193 products.

I restored the database from the dump taken before the import. The variant count returned to 1,263, the cache was cleared, and the storefront was checked before another write was allowed. The fix reused the mapping recorded by the earlier catalogue cleanup and applied it before donor product cards were merged. A command-level regression test then checked the real entry point, because calling the two functions in the right order inside a unit test did not prove that the import command did the same.

The first correction protected incoming data. It did not clean point sizes already stored in older cards. A later import exposed that second layer on 40 cards. A separate cleanup checked each point value against eleven kinds of references before removing it: 169 values removed, none skipped, with the dry run and write run producing the same result. A repeat on hidden cards used the same guarded path.

The importer had also been overwriting prices, size surcharges and discounts that the client maintained in the store. I built a small preview-and-apply tool for spreadsheet updates instead. On its first recorded use, the client uploaded 198 rows; 124 changed and the tool reported no errors. This is the only run preserved in the work log; there is no recorded result for later uploads.

Money was read from the wrong moment

Before live payments, a reservation could expire while the buyer was still passing 3-D Secure. The payment could then complete against a cancelled order while the confirmation page still said success. The correction added an in-flight mark, a grace period and an order lock. A late payment restores the order only if stock still allows it; otherwise the payment is refunded automatically.

The first live payment incidents revealed another class of error. Two preorder buyers chose a 10 percent prepayment and were charged the full amount. A separate reproducing order showed the checkout asking for 10 percent while the CloudPayments widget received 100 percent. The payment page created a new empty cart, and a hook read that context cart before the explicit order snapshot. With no preorder plan left, the first payment became the whole debt.

I chose a small server-side guard. The order passed in explicitly wins over the cart in context: by the time of payment the context cart can already be a different, new and empty one, while the amount and the prepayment plan belong to the order. The notification handler refuses an amount that does not match the current debt: the amount has an owner, the order, and a different number means someone counted the money in the wrong place. The reproducing test failed on the old code first. The same assumption then turned up in the discount handler, so the final check walks every handler in that hook family and requires order data to take priority.

A third incident came from a value that was true when an item entered the cart and stale by checkout. The rule moved to the stock snapshot stored on the order itself. Before I accepted the change, the new rule was replayed read-only across 77 production orders. Exactly one result changed, the incident the rule was meant to correct. The client handled the earlier charge with the buyer outside this code path.

CDEK accepted the request, then rejected the parcel

CDEK could return 202 Accepted and reject the parcel four seconds later. The reverse was possible too: the store's request timed out while CDEK still created the parcel. A blind retry would create a second shipment because the service did not deduplicate on the store's order number.

Across the review rounds, eleven critical findings came back to one unsafe assumption: that the absence of a clean response proved the absence of a parcel. The integration now asks CDEK for its final state and separates an unknown result from a confirmed rejection. A cancellation that arrives during the request is kept instead of being overwritten by the late response.

The sandbox could demonstrate rejection but never a successful final state. With the client's permission, the acceptance plan allowed one real waybill on a controlled order, followed by deletion. That run found another defect before automation was enabled. A mixed order then produced separate waybills for its normal and preorder parts, and only after those checks did the service begin receiving orders automatically.

A later defect sat in the moment of dispatch itself. A shipment was created on any paid status, so a carrier could receive a parcel that would never exist. I moved the rule for when an order is ready to ship above the carriers, into its own module that CDEK and Yandex Delivery ask instead of deciding for themselves. Before the change, a carrier answered that question with a non-empty list in 26 cases out of 37; after release, eight orders in shipped states returned an empty list, as they should.

Product marking ran in production on the second day

Clothing in Russia falls under the Chestny Znak marking scheme, and marking was on the list of things the store could not launch without. On 22 September I checked the production till: receipts were already in fiscal format 1.2, 60 out of 60, and none carried a marking code. Reading the government decrees themselves, No. 1956 §76, No. 1944 §3(e) and No. 174 §3, I chose the lighter scheme: a prepayment receipt at checkout, withdrawal from circulation by a remote-sale document at shipment, and a closing receipt with a code for every item at handover. The earlier estimate had been 14 to 25 days; this scheme came to 7 to 10.

In practice it ran in production on 23 September at 15:19 Moscow time. The rule that a handed-over item closes its payment lives in a module that belongs to neither the till, the warehouse nor a carrier: it asks participants what they can do rather than who they are, so a second till or a new carrier does not touch shared code. The handover log keeps its invariants in the database. The receipt key is written before the till is called, so a lost answer from the till cannot produce a second receipt. Handovers from before the install are left alone; otherwise the first run would have issued receipts for every parcel since 14 September.

Review ran for six rounds, each from its own angle. The fifth found that the fourth round's fixes were not wired in: an adapter rebuilt the answer from keys it already knew and dropped the new ones. The sixth checked the tests themselves, and some of the new ones passed on broken code, showing a guard that was not there. They were rewritten and checked by mutation: remove the guard and the test has to fail. By release there were 1,155 automated checks, and the key ones now fail when the thing they guard breaks.

That same evening the client asked why one item in an order carried two marking codes. MoySklad stores the same code in two fields, the store's parser read both, and every item got its code twice. That hit the receipts and the daily reconciliation, which compares codes withdrawn from circulation against shipments and writes to the client about every mismatch. The fix was in production the next day: a shipment of five items went from ten codes to five, one of two items from four to two, one of a single item from two to one. Reconciliation found one mismatch instead of eight, and that one was real: the document for a single shipment had been rejected.

The shop was selling, but the project was not finished

A snapshot of the production database on 29 September. From 9 to 29 September the store took 101 orders from 91 buyers. 70 orders were paid, 142 items at an average of 7,366 RUB, and 40 of them included a preorder. Another 28 orders were cancelled; a reservation lapses on its own if payment does not arrive within 15 minutes. Delivery went to 48 orders by Yandex and 22 by CDEK, all to pickup points, and every order reached MoySklad, 101 out of 101.

The online till took 347,980 RUB across 85 payments and returned 12,450 RUB in five refunds. These are successful payments in the till, not a bank statement. The orders themselves add up to more, 515,598 RUB, because buyers pay the rest of a preorder when the item arrives. Beyond orders, 164 people asked to be told when an item is back.

All of this happened before the official launch. I had hidden the site from search engines from the start so it would be harder to stumble on, and as far as I know there was no paid advertising. But the brand was not new: it has sold on a marketplace for a long time, it has its own audience, and the owner mentioned the site on her blog, marked as still in development. The first buyer found the site on her own, by the brand name, and ordered without anyone's help. The client had not expected it and was glad. The brand created the demand; the site took it and carried it through payment, receipts, the warehouse and delivery. I deleted the test orders with the client's permission before counting: 48 orders and 39 buyers.

Live operation changed the work. An incident could span the shop database, the payment provider, a receipt, the accounting system and a delivery service. Before changing money or order state, I reconstructed that chain from read-only data, wrote down the planned change and took a database dump.

By early September the project was stalling on hanging questions and requirements, and management asked for them to be collected. I kept the open questions in my own source archive, each linked to the material it came from, so on 4 September the complete list went to management at once, without rebuilding it from memory. So that AI would not turn everything into a question, I allowed reversible decisions the status of an assumption: the decision is written down with the cost of being wrong and can be corrected later. On 8 September the full list went out again; the reaction was mixed, and I fixed the part of it that was fair. After that the task was clear: prepare the store fully for launch, test everything that could be tested and write down the gaps. The first real payment went through the next day.

By 28 September the main scope was done, but the project was not closed. The client was still accepting the legal copy and walking through the site as a buyer, returns of marked goods were waiting for real Data Matrix codes from the warehouse, and indexing will be switched on at launch. The store has not been tested under heavy load, so this case claims no production scale.

How it is built

Architecture
  • Every number has one owner (money belongs to the till, stock to the warehouse), business rules stay apart from integrations, participants are asked by capability through a shared interface, and a shared rule sits above the implementations without knowing their names. An abstraction appears on the second occurrence, not the first.
  • The PrestaShop core is not patched: everything is built as 22 custom modules on hooks, one responsibility per module. Two unavoidable core fixes live as scripts with a check after every update.
  • The “time to ship” rule sits above the delivery services and asks them by capability: a new service adds one method of its own and shared code stays untouched.
  • The “delivered, close the settlement” rule is shared too. Each service translates its own word into a store event, and the module asks participants for money, marking codes and the receipt by capability; a parity test rejects a service without the required contract.
  • Catalogue import lives outside the store, as a separate Python tool between a source and a sink: a second source is added next to the first and the importer does not change.
Infrastructure
  • Docker Compose: MariaDB 11 with a health check and PrestaShop 9.1.4; only nginx with a certificate faces the outside.
  • PHP and Apache settings are pinned in the repository so an image update cannot reset them.
  • Background jobs on cron: reservations and the warehouse and notification queues every minute, Yandex every 5 minutes, stock every 30 minutes under a lock, the marking reconciliation every hour.
  • Deployment is manual, with a database dump beforehand and a check of server files against git.
Fault tolerance
  • A till notification is checked against its HMAC-SHA256 signature before any field is read. The amount is matched against what the order still owes, the money trail is written before the status changes, a repeated notification changes nothing, and the order is held under a database lock.
  • The receipt key is written before calling the till, and an uncertain outcome forbids automatic retries, so there is no second receipt. A single switch turns off the money operation.
  • The notification queue makes 9 attempts at intervals from a minute to 6 hours and honestly promises at-least-once delivery.
  • The external order number for a delivery service is issued once and stored: recomputing it would create a second request. For CDEK an unknown outcome is kept apart from a confirmed rejection.
  • The database is copied every night and kept for 30 days, images for 14 days.
Data and AI
  • There is no AI in the store itself; it was used only in development.
  • Stock comes straight from the warehouse system: zero in stock means sold.
  • The seller is copied into the order line when the order is placed, so old reports are never rewritten after the fact.
  • Marking withdrawal is reconciled every hour: a shipment older than a day without accepted codes produces a message to a person, and a marking system failure is reported at once.
Decisions and assumptions
  • Reversible decisions were closed with a written assumption instead of an open question: the seller and the till, a 60-day “new arrivals” window, the preorder layout and the promo code. The assumption status entered the mnemo standard on 1 September, so that the project would not wait on questions that can be decided now and corrected later.
  • In early August, while the store was still closed, Meta's indexer arrived: 762 thousand requests and 16.6 GB in three days, almost all of them in the trap of a faceted filter that produced 247,769 new URLs a day. It could have been cut off at the entry server or with a web server rule; I started with the cheapest, risk-free step, a named line in robots.txt, and the next night it left. It never requested robots.txt itself, though, so the cause is not proven.
  • A custom CDEK module instead of a bought one; at first it only calculated delivery.
  • The declared value of a parcel is taken before basket discounts, on purpose: there is no insurance and no cash on delivery, and the condition for revisiting it is written down.
  • A refund against one of an order's two payments is chosen automatically only when the match is unambiguous; otherwise no money moves.
  • Marking does not retroactively close deliveries that happened before the module was installed.
