W-03Case

Real orders before the official launch

I directed the implementation of a PrestaShop store in a stack that was new to me, using AI agents for the code and a separate reviewer before production. The work started with the catalogue and grew into payments, receipts, stock, CDEK and Yandex Delivery. The project began on 24 July 2026; 47 days later, on 9 September, the first real payment went through. The launch checklist and final client acceptance were still open.

From requirements to real orders

Management handled the client relationship. I received the requirements, chose the technical direction and carried the work through implementation, review and acceptance. The stack was new to me, so I used AI agents to inspect the platform and write the code. I was responsible for the user flows, the boundaries between systems, production checks and the final engineering decisions.

The shop had to support several sellers, take catalogue data from marketplaces, handle partial prepayments, synchronise stock and route orders to two delivery services. I chose PrestaShop after checking those requirements on a live stand. Its native model could represent the size ranges, the official YooKassa module installed without a patch, the delivery sandbox returned 13 rates and 20 pickup points, and an API stock write recalculated the aggregate. YooKassa was useful for validating the platform choice; we later chose CloudPayments and a custom module for the production payment path.

The store eventually included catalogue imports, CloudPayments, online receipts, stock synchronisation, marketplace data, CDEK and Yandex Delivery. At the 22 September 2026 snapshot, the repository contained 20 custom modules. Thirteen module suites completed 1,343 assertion checks offline. These were hand-written runners; the repository still had no CI.

The first real payment went through on 9 September. The next day, an order completed payment, receipt, stock and delivery processing without the team moving it by hand.

The catalogue passed the wrong check

One import increased the catalogue from 1,263 to 1,857 variants while reporting no errors and no duplicate size values. The source supplied point sizes such as 90; the store had already normalised the same size to a range such as 80-90. A string comparison treated them as different, so both survived on 193 products.

I restored the database from the dump taken before the import. The variant count returned to 1,263, the cache was cleared, and the storefront was checked before another write was allowed. The fix reused the mapping recorded by the earlier catalogue cleanup and applied it before donor product cards were merged. A command-level regression test then checked the real entry point, because calling the two functions in the right order inside a unit test did not prove that the import command did the same.

The first correction protected incoming data. It did not clean point sizes already stored in older cards. A later import exposed that second layer on 40 cards. A separate cleanup checked each point value against eleven kinds of references before removing it: 169 values removed, none skipped, with the dry run and write run producing the same result. A repeat on hidden cards used the same guarded path.

The importer had also been overwriting prices, size surcharges and discounts that the client maintained in the store. We built a small preview-and-apply tool for spreadsheet updates instead. On its first recorded use, the client uploaded 198 rows; 124 changed and the tool reported no errors. This is the only run preserved in the work log; there is no recorded result for later uploads.

Money was read from the wrong moment

Before live payments, a reservation could expire while the buyer was still passing 3-D Secure. The payment could then complete against a cancelled order while the confirmation page still said success. The correction added an in-flight mark, a grace period and an order lock. A late payment restores the order only if stock still allows it; otherwise the payment is refunded automatically.

The first live payment incidents revealed another class of error. Two preorder buyers chose a 10 percent prepayment and were charged the full amount. A separate reproducing order showed the checkout asking for 10 percent while the CloudPayments widget received 100 percent. The payment page created a new empty cart, and a hook read that context cart before the explicit order snapshot. With no preorder plan left, the first payment became the whole debt.

I chose a small server-side boundary: the explicit order takes priority over the context cart, and the notification handler refuses an amount that differs from the current debt. A reproducing test failed on the old code before the change. The same assumption then turned up in a discount listener, so the final guard walks every listener in that hook family and requires order data to win over cart data.

A third incident came from a value that was true when an item entered the cart and stale by checkout. The rule moved to the stock snapshot stored on the order itself. Before I accepted the change, the new rule was replayed read-only across 77 production orders. Exactly one result changed, the incident the rule was meant to correct. The client handled the earlier charge with the buyer outside this code path.

CDEK accepted the request, then rejected the parcel

CDEK could return 202 Accepted and reject the parcel four seconds later. The reverse was possible too: our request timed out while CDEK still created the parcel. A blind retry would create a second shipment because the service did not deduplicate on our order number.

Across the review rounds, eleven critical findings came back to one unsafe assumption: that the absence of a clean response proved the absence of a parcel. The integration now asks CDEK for its final state and separates an unknown result from a confirmed rejection. A cancellation that arrives during the request is kept instead of being overwritten by the late response.

The sandbox could demonstrate rejection but never a successful final state. With the client's permission, the acceptance plan allowed one real waybill on a controlled order, followed by deletion. That run found another defect before automation was enabled. A mixed order then produced separate waybills for its normal and preorder parts, and only after those checks did the service begin receiving orders automatically.

The shop was selling, but the project was not finished

By 22 September 2026, this was already an operating system rather than a catalogue demo. Real buyers could place and pay for orders; the shop issued receipts, changed stock, reserved goods in the accounting system and sent orders to CDEK or Yandex Delivery. Mixed orders split normal and preorder items into separate shipments. When a partly paid order needed a quantity or product correction, our team handled it as a controlled production change.

Live operation changed the work. An incident could span the shop database, the payment provider, a receipt, the accounting system and a delivery service. Before changing money or order state, I first reconstructed that chain from read-only data, wrote down the proposed mutation and took a database dump. Delivery acceptance included one controlled real waybill because the sandbox could not prove a successful final state.

I kept the open questions in my own source archive, each linked to the material it came from. That made it possible to put the complete open list in front of management on 8 September without reconstructing it from memory.

The project was still not complete. Search indexing remained disabled, CDEK courier delivery was outside the verified path, and the closeout list still included partial purchase, the fast-payment path, legal copy, the product-marking boundary and final client acceptance. The store had not been tested at high volume, so this case does not claim a completed launch or production scale.
