W-03Case

The contract path from order to fiscal receipt

I ran the backend of a contract project: a site where a client builds an order in a configurator, pays online and receives documents in a personal cabinet. In five weeks I took it from someone else's skeleton to a production server, then through three waves of client changes. I counted a payment as finished not on the gateway's word, but only when the internal state agreed and a fiscal receipt existed.

The project started before me

The first commits in spring 2026 were not mine: a Django skeleton, pages built from a prototype, price lists from spreadsheets. Until 22 May production was edited outside git. On 1 June I took over the project with a specification in five stages, and the client paid the first advance the same day.

The work ran along a chain of three links. Our client was itself a contractor for its own client, and requirements, answers and acceptance went through it and through my management; they reached me as forwarded messages. The end client took a long time to agree on anything, so every decision took days and sometimes weeks, and the project stretched out further than its scope required.

I began with a read-only survey of the servers. It showed that the code in production was newer than the repository; a colleague synced production with git and I checked the result line for line. Only then did work go stage by stage: accounts, pricing, payment, emails, the cabinet.

I ran the project alone. AI agents wrote the code, every change went through subagent review until LGTM, and money and sign-in also had a second reviewer from another model: on 10 June it twice caught what the first one missed. On 11 June the separate frontend was cancelled and my Django interface became the final one, so the client side joined the backend.

The price came from the browser

On 5 June price calculation moved to the server. Five days later it turned out not to be enough: the storefront still sent orders to an old handler where the browser supplied the price, and the order was not linked to the cabinet. Anyone who opened the developer tools could have paid whatever they liked.

On 15 June the client-side calculation was removed completely. A value from the browser became input for display, not the amount to pay: only the server computes the amount, and the payment handler checks against that same figure.

A payment is finished when there is a receipt

I treated the gateway's success response as an intermediate event. The notification handler checks the signature first, then locks the payment and order rows, checks the amount and only then changes state. A repeated notification gets an “accepted” answer and changes nothing, and a failure in one subscriber to the payment event does not break the payment itself.

I drew the boundary myself and wrote it down: refunds and fiscalisation stay on the gateway's side, and the site stores the receipt data and links to it. That way the project took on nothing it should not do and was not left without proof of payment.

Before real money the path went through a simulated signed notification with the real secret: a repeat gives the same payment, a broken signature is refused. On 23 June I checked it with a real payment on the test server. One item's price was lowered to 100 RUB for the test, the order went through the storefront, then payment, notification, “paid” status, a 54-FZ receipt with fiscal keys from the operator, and the emails.

The rest of the path surrounds the payment. Emails to the client go out only when the status visible to them changes, and only after the transaction commits: review caught a task queued inside the transaction that could have sent an email about a change that never happened. Document scans sit outside public storage and are served only to staff and the order's owner; on the old production site five such scans had been open to a direct link.

Audit, release and the first deployment mistake

On 25 June four subagents reviewed the code by area: orders and payments, configurators and prices, sign-in, core and content. The payment core came through with no findings, and I closed the other P1 and P2 findings. One P2 I left on purpose: the regression risk outweighed the benefit.

On 8 July the project went to the production server. I created the database there from scratch so the user model would not have to change on live data. Two days later came the first deployment mistake: a stray ./ in an rsync command overwrote the settings file and broke the Python environment, and the site was down for a few minutes. The database was untouched, and a rule stayed: deployment uses an explicit list of files only.

Three waves of changes and a bug the project made itself

After that the client sent changes in waves: 7 items on 22 to 24 July, 11 items on 31 July, 5 more at the end of September. All were closed; by the end of the second wave there were 663 tests.

The nastiest turned out to be a bug the project introduced itself on 1 July. The delivery price went from a template into JavaScript as a number with a decimal comma. In two configurators that killed the whole script, and in the third courier delivery cost 0 RUB. From 8 July the bug lived in production until I found and fixed it on 24 July. A day earlier the same comma in another constant had left the personal cabinet empty; that one surfaced from the client's screenshot.

Urgent orders needed automatic cancellation when unpaid. The server has no queue worker, so instead of a delayed task that would pile up dead, I made a scheduled command plus a guard in the payment itself: an expired urgent order cannot be paid. At the client's request the window later grew from 5 to 15 minutes.

I deployed the third wave on 28 and 29 September with the new deployment script and its dry run for the first time; by then there were 684 tests.

After handover: what the logs showed

On 13 August, with the client silent for a week after a wave was handed over, I went through 13 days of production logs. One endpoint's response size jumped between 82 and 5,327 bytes. The cause was the API settings: the renderer list was not set, so any request from a browser got the debug interface instead of data. A public reference endpoint returned 10,751 bytes instead of 1,767. I set the list explicitly, and the debug interface is now switched on by an environment variable.

The same review found the deployment script inherited from the first commits. It synced the directory with --delete and on its first run would have wiped the database backups from the server, including the copy taken before the change wave. It had not yet been run against production. I rewrote it to an explicit list of paths, and review found two places in the new script where an rsync or static-build failure was reported as success; both were reproduced with a real failure and closed. I did not make the new script's first run against production: I updated production by hand with the same explicit list.

A new stage: agree first, build later

Since 15 September a new stage has been under negotiation: cabinets for companies and for partners with branches. No code is written for it until what to build is agreed. The first document was a technical confirmation for the client: one Django application with no separate partner program, separation by role, organisation and branch on the server side, a future CRM as a separate internal contour, and company sign-in by tax number or by a login issued by an administrator.

Next I put together my own contractor's specification and estimate, compared the client's specification with what already existed, and reproduced in production eight of the client's remarks about delivered work, two of them about money. When the mock-ups arrived the estimate grew from 65.5 to 77.5 working days, with a separate sheet of open questions.

On 28 September a new package arrived: 19 annotated screenshots and a call recording. Two annotations contradicted decisions already confirmed: when an order enters the partner's report, and what the final chain of statuses with a refund looks like. I did not send the question around again through management; I wrote down a working interpretation with its reasoning. An order enters the report on its first move to “In progress”, because the note right on the report screen is more specific than a general arrow from the checkout button. “Issued”, “Documents at the partner” and “Client received” became three separate events. Both interpretations went on the agenda for a joint review.

The same package lowered the load requirement from 1,000 to 100 concurrent users, and I researched the integration with the companies' bank first. The bank's documentation covers exchanging payment documents and statuses, but there is no public API for creating an invoice in its cabinet. Hence the baseline: the site generates the invoice, and the payment status comes from the bank and is matched by amount and description, estimated at 7 to 12 working days. The digital rouble and cards from CIS countries went to a future backlog.

The client package on 28 September: a 34-page album of screens, two pages of questions and a 25-page specification. Five urgent configurator changes stood in it as a separate stage not yet done, but the next day management decided to ship them at once, and on 29 September they went to production. Negotiation of the main stage continues.

Where the project stands

The site has run on the production server since 8 July. By 29 September it held 16 orders, but no real payment has yet gone through in production: the only real payment happened on the test server, whose database was not carried over. Meanwhile the new stage is being negotiated.

There is no load on the site yet, and the reason is the same chain rather than the technology. From 3 to 7 August the client tested the site closely, and then the calculations in the logs stopped; two changes they had asked for themselves were still unchecked by mid-August. From mid-August to mid-September the project left my desk altogether: it was being discussed further up the chain while I worked on other projects. It came back as a new stage.

There was no external security audit and no load test, and the response-time criterion for a hundred users was never measured. Backup recovery was rehearsed as a migration on a copy of the database, not as a production restore. A small drift between the repository and the server remains in the auto-cancel schedule and the application server port, and it is written down.

How it is built

Architecture
  • One place where an order's status changes, emitting the payment and status events; enums and the API contract in one place with an OpenAPI snapshot test.
  • 13 apps by domain. The rule from the project's architecture document: an abstraction appears only if it costs almost nothing and pays off. So ports and adapters sit where there is an outside party that tests need to fake or that may change: mail, sign-in through an external provider, the payment gateway. There is no repository layer over the Django ORM: for ordinary data operations it would double the code and give nothing back.
  • Page texts live in one registry of blocks that an administrator edits, not a developer.
Infrastructure
  • Python 3.13, Django 5.2, gunicorn behind nginx with a Let's Encrypt certificate, PostgreSQL 16.
  • Redis shared with other sites on the server, with the project's own database numbers. There is no queue worker, tasks run immediately, and periodic jobs run on a schedule.
  • A daily database dump with rotation and a snapshot before every deployment.
  • A deployment script with a dry run and an explicit list of paths; a failure at any step shows as a failure.
Fault tolerance
  • Payment notification: signature before anything else, row locks on the payment and the order, an amount check, and a repeat without reprocessing.
  • The order number comes from the primary key, which closed a race that caused a 500 error. A promo code is spent under a row lock.
  • Emails go out after the transaction commits and only when the visible status changes.
  • An expired urgent order cannot be paid even if the auto-cancel schedule has not run yet.
Data and AI
  • There is no AI in the product.
  • Document scans sit outside public storage and are served only to staff and the order's owner; old files were moved by a command.
  • A legal review under the Russian personal data and fiscal receipt laws for an anonymous order was done before the code.
  • The gateway and the fiscal data operator issue the receipt; the site stores its keys.
Decisions and assumptions
  • Refunds and fiscalisation stay with the gateway; the site stores the receipt data.
  • Create the production database from scratch rather than carry it over from the test server.
  • Leave one P2 audit finding: the regression risk outweighs the benefit.
  • Do not make the new deployment script's first run against production; update production by hand with an explicit list.
  • Auto-cancel on a schedule instead of a delayed task, since there is no queue worker.
  • Contradictory client annotations do not stop the work: a working interpretation is written down with its reasoning and taken to a joint review.
