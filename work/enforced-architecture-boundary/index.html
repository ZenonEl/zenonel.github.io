An architecture boundary became a check that fails

Splitting a Python monolith is easy to draw and hard to keep. I moved external systems behind ports and adapters, then wrote an AST check so the dependency direction survives the next person in a hurry.

01Safe context

Domain logic and infrastructure concerns were mixed inside a Python monolith. Business rules imported database and third party client code directly, so testing a rule meant standing up everything around it.

The team had a diagram of the intended structure. The code did not agree with it, and nothing noticed.

02Constraints

  • The system stayed in use throughout, so the migration had to arrive in small reviewable steps.
  • The result had to be understandable by people who had not read an architecture book that week.
  • Any rule I introduced had to be cheap to run on every change, or it would be skipped.

03What was mine

I chose the boundary, moved external systems behind ports and adapters, sequenced the migration, and wrote the check that holds the direction.

I also chose where to stop. The goal was one useful direction of dependency, not maximum abstraction.

04Team and agent boundary

Agents were useful for the mechanical part of the migration and for finding every import of a module. Deciding what belongs in the domain was not something I handed over.

The AST check itself is small enough to read in one sitting, which matters more than how it was drafted.

05Alternatives I weighed

  1. Document the rule and rely on review

    Free to introduce. It works until a deadline, a new joiner, or a large diff. Rejected, because the previous diagram had already failed the same way.

  2. A linter plugin or an off the shelf import checker

    Reasonable, and worth revisiting. At the time a short AST check tuned to this one rule was easier to explain and had no configuration surface to drift.

  3. A full rewrite into services first

    Rejected. The dependency direction was the actual problem. Moving unclear boundaries into separate deployments would have made them permanent.

06Decision

Put external systems behind ports, implement them as adapters in infrastructure, migrate in small steps, and enforce the one rule that matters with an AST check that fails.

I also introduced one result contract with an explicit status and a restartable flag. Callers could then distinguish no data from a failed run instead of guessing from an empty payload.

07Implementation

  • Ports defined in the domain as plain interfaces.
  • Adapters in infrastructure implementing those ports.
  • A common result contract carrying status and whether the operation can be restarted.
  • Small migrations, each one reviewable on its own.
  • An AST check that walks the source and fails when a domain module imports infrastructure.

Service names, the repository layout, and the CI provider are left out because they would identify the system.

08How I verified it

The check earns its place by failing. I confirmed that it fails on a deliberately reintroduced import, then let it run on every change.

Independent review caught a different failure that unit tests had missed: the graph library recursively expanded a nested state object, so the real graph path failed even though the isolated tests passed. I fixed the integration path and kept the case as a warning against testing only below the framework boundary.

  • A forbidden import added on purpose, to see the check reject it.
  • Domain tests run without infrastructure present.
  • Each migration step reviewed as its own change rather than one large diff.

09Result

The main orchestration module shrank from 976 to 647 lines while its responsibilities moved behind explicit boundaries. The domain layer no longer imports infrastructure, and an attempt to reintroduce that dependency fails the check instead of passing review.

10What this does not prove

The check enforces one rule about import direction. It does not verify that the boundary is in the right place, and a determined workaround at runtime can still cross it.

Ports and adapters suited this boundary. It does not follow that every Python or Django application needs the same structure.

11What I would change now

I would add the same check to the application layer, because the rule I enforced is the one I happened to break first.

I would also record the rule next to the code it protects, so a reader meets the constraint before the failure message.
