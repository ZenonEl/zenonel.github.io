Cost per answer became a measurable property

LLM spending was visible as a monthly total and nothing smaller. I made it a per-call property, then used the same discipline to reject a retrieval change that looked better only on its own metric.

01Safe context

A product feature answered user questions with a retrieval step in front of a language model. Spending on the model was visible as a total for the period. Latency was visible as a general impression of slowness.

Neither view could tell me whether a cache change or a shorter context helped, because there was no per-request number to compare.

02Constraints

  • The answer quality could not drop while the cost work happened.
  • Changes had to land in a running product, so a rewrite was not on the table.
  • The labelled evaluation set had to be small enough that one person could keep it honest.

03What was mine

I introduced the accounting, chose what to change in the cache and the context, ran the before and after measurement, and made the call on the retrieval design.

The decision to reject the nicer looking retrieval option was mine, and I recorded the reason so it would not come back as an untested idea.

04Team and agent boundary

I used AI agents to inspect unfamiliar parts of the pipeline and to draft changes. The measurement design, the labelling of the evaluation set, and the accept or reject decision were not delegated.

Generated code stayed a draft until I had read it, run it against the labelled set, and checked the failure paths.

05Alternatives I weighed

  1. Reduce the model tier and keep everything else

    Cheap to try and easy to measure, but it moves quality and cost at the same time, which makes the result hard to attribute. I kept it out of the first change so the cache and context effect stayed readable.

  2. The retrieval design that improved its own metric

    One proposed retrieval change raised the metric it was tuned for and lowered recall on the labelled set. I rejected it. A metric that improves while the thing it stands for gets worse is a reason to stop, not to ship.

  3. Per-call accounting first

    Slower to show a win, but it is the only option that makes every later change comparable. This is what I did.

06Decision

I recorded cost, token counts, and latency for every model call, keyed to the request that caused it. The numbers showed two different problems: cache hits depended on which provider site received the request, and the verification layer was reading far more context than it used.

I pinned the cache-sensitive path to one provider site and narrowed verification to the passages cited by the draft, with a lexical fallback when the citation was incomplete. Retrieval changes still had to pass the labelled set.

07Implementation

  • Per-call accounting attached to the request, so one answer keeps its cost, token count, and latency.
  • Provider placement fixed for the path whose prefix cache otherwise hit roughly every other request.
  • Verification context reduced from the whole knowledge base to cited passages, with a lexical fallback.
  • A fixed set of 37 hand-labelled questions used as the retrieval comparison.

Storage and dashboard details are left out because naming them would identify the system.

08How I verified it

I compared the same path before and after the change rather than two unrelated totals, and I kept the rejected retrieval option in the record with the number that killed it.

One retrospective run initially looked better than it was. The system had learned from some of the questions after they were asked, so the later knowledge base leaked into the earlier measurement. I discarded that result and recomputed it against the state that existed at request time.

  • Cost and latency held at request level, not aggregated first.
  • The same question set replayed on both sides of the change.
  • Recall checked on the labelled set for every retrieval candidate.

09Result

Cost per answer fell from 23 to 8.8 roubles in the controlled production measurement, 62 percent. The verification layer fell from $0.0600 to $0.0047 per answer, with input shrinking from 38,268 to 2,970 tokens and latency from 7.6 to 2.7 seconds.

The comparison on 37 hand-labelled questions stopped a retrieval change whose best alternative covered only 57 to 62 percent of the required material.

10What this does not prove

The 62 percent figure comes from nine production requests. Traffic was small, and the question series favoured prefix caching, so I do not turn it into a monthly forecast.

37 labelled questions is a small set. It was enough to reject a clearly worse option. It is not enough to rank two close candidates with confidence.

11What I would change now

I would grow the labelled set and record its inter-rater agreement before using it to compare close options, because the current set can only reject the obvious loser.

I would rerun the production comparison on a larger and less cache-friendly sample before using the percentage in a capacity or budget forecast.
